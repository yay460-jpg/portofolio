# Lithosite Mine Services — Report Flow

## 1. Purpose

This document defines the end-to-end flow used by Lithosite Mine Services to transform Work Control data into management reports.

The flow separates live operational data, validation, KPI calculation, report aggregation, report review, and final PDF issuance.

    ├── Operations
    ├── Equipment
    ├── Work Front

    └── Map / Topography

## 3. Layer Responsibilities

### 3.1 Work Control Layer

Work Control is the operational source layer.

It contains the records and evidence generated by the site's work activities. The reporting layer must consume these records and must not create a second operational source of truth.

### 3.2 Data Validation Layer

Before report aggregation, source data is checked for completeness and validity.

Examples:
- required dates and identifiers
- valid time boundaries
- valid equipment references
- valid work-front references
- maintenance boundaries
- HSE event completeness
- issue status
- spatial marker validity

Invalid or missing information must remain visible as a validation condition.

### 3.3 KPI Foundation Layer

Validated data is transformed into derived KPI evidence.

Primary fleet metrics:
- Scheduled Time
- Available Time
- Used Time
- PA
- UA
- EU

KPI calculations must preserve the active policy:
- time baseline
- EU denominator
- effective-time rule
- reporting date/scope
- eligible/excluded population
- validation issues

Finalized KPI snapshots are preferred for issued reports where available.

### 3.4 Report Engine

The Report Engine assembles a report model from validated source data and KPI results.

It does not directly format PDF pages.

Its responsibilities are:
- select reporting period
- select scope
- aggregate source records
- calculate report summaries
- build trends
- identify exceptions
- collect outstanding actions
- attach evidence references
- preserve KPI lineage
- produce a stable report snapshot

### 3.5 Report Periods

#### Daily

Question:

> What happened today?

Focus:
- completed work/tasks
- current equipment condition
- work fronts
- HSE events
- maintenance/downtime
- material movement
- issues
- KPI
- outstanding work
- spatial evidence

#### Weekly

Question:

> How are we performing this week?

Focus:
- planned vs actual
- KPI trend
- equipment performance
- work-front progress
- HSE summary
- downtime
- material movement
- recurring issues
- outstanding actions
- management concerns

#### Monthly

Question:

> What does management need to know or decide?

Focus:
- executive summary
- target vs actual
- monthly KPI
- equipment performance
- work-front progress
- HSE performance
- downtime
- material movement
- major/recurring issues
- outstanding actions
- trends
- management attention
- recommendations

## 4. Report Generation Flow

### Step 1 — Select Report

User opens Report Center and selects:
- Daily
- Weekly
- Monthly

### Step 2 — Select Period

The user selects the reporting date or period.

The system resolves:
- period start
- period end
- site/scope
- applicable KPI policy

### Step 3 — Collect Source Data

The system reads the relevant Work Control domains.

Only data belonging to the selected scope and period is included.

### Step 4 — Validate

The report engine validates the collected source data.

If required data is incomplete, the report must enter:

`VALIDATION REQUIRED`

It must not silently convert missing values to zero.

### Step 5 — Resolve KPI

The engine loads or calculates the applicable KPI result.

For issued reports, a finalized KPI snapshot should be used when available.

### Step 6 — Build Report Model

The engine creates a normalized report model containing:
- report identity
- period
- summary
- KPI
- domain summaries
- trends
- issues
- actions
- evidence references
- validation status
- lineage

### Step 7 — Review

The report is presented as a preview.

The reviewer checks:
- summary
- KPI
- exceptions
- issues
- actions
- evidence
- validation status

### Step 8 — Issue

When valid, the report changes to:

`ISSUED`

The issued report receives:
- report ID
- generation timestamp
- source snapshot/lineage
- application version
- report revision

### Step 9 — Render PDF

The stable report model is passed to the PDF renderer.

PDF rendering must not query live Work Control data again.

### Step 10 — Delivery

The final PDF is delivered to the intended audience:

- Supervisor
- Manager
- BOSS 01

## 5. Snapshot Principle

The critical rule is:

> **Live data can change; an issued report must not.**

Therefore:

```
LIVE WORK CONTROL
       │
       ▼
 REPORT SNAPSHOT
       │
       ▼
     PDF
```

The PDF is generated from the report snapshot, not from live UI elements.

## 6. Report Status Flow

```
DRAFT
  │
  ▼
VALIDATION
  │
  ├──────────────► VALIDATION REQUIRED
  │                       │
  │                       └── correction → VALIDATION
  │
  ▼
READY
  │
  ▼
ISSUED
```

An issued report should be treated as immutable.

## 7. Evidence Flow

Evidence follows the source record:

```
Source Record
    │
    ├── Domain
    ├── Record ID
    ├── Date / Time
    ├── Status
    └── Spatial Reference
             │
             ▼
       Report Evidence
             │
             ▼
          PDF / Appendix
```

The executive sections should remain concise. Detailed evidence can be placed in appendices or referenced back to the system.

## 8. Management Information Flow

The reporting system intentionally moves from detail to decision support:

```
RAW WORK
   ↓
VALIDATED DATA
   ↓
KPI / DERIVED EVIDENCE
   ↓
DAILY FACTS
   ↓
WEEKLY TRENDS
   ↓
MONTHLY MANAGEMENT INSIGHT
   ↓
DECISION / ACTION
```

This prevents the Monthly report from becoming a simple compilation of Daily reports.

## 9. PDF Design Rule

The PDF is a presentation layer only.

Business rules belong in:
- source domains
- validation
- KPI Foundation
- Report Engine
- Report Contract

PDF code must only render the already-approved report model.

## 10. Future Extension

The same report model may later support:
- PDF
- XLSX
- CSV
- management dashboard
- email delivery
- scheduled report generation

The underlying report contract should remain unchanged when a new output format is added.
