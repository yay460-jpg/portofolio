# Lithosite Mine Services — Report Output Contract

## 1. Purpose

This contract defines the reporting layer for Lithosite Mine Services. It separates reporting rules from PDF rendering so Daily, Weekly, and Monthly reports use a consistent, traceable source of operational data.

The report layer is an output layer above Work Control data. A PDF is a rendered snapshot of a report; it is not the system of record.

## 2. Reporting Hierarchy

| Report | Primary question | Primary audience |
|---|---|---|
| Daily | What happened today? | Supervisor, Manager, BOSS 01 |
| Weekly | How are we performing this week? | Manager, BOSS 01 |
| Monthly | What does management need to know or decide? | Manager, BOSS 01 |

Reports must not be implemented as the same report with different date ranges. Each period has a different management purpose.

## 3. Report Identity

Every generated report must carry:
- report type: DAILY, WEEKLY, or MONTHLY
- reporting period start and end
- site/scope
- report ID
- generated timestamp
- application/version identifier
- source data snapshot or equivalent immutable lineage reference
- report status

A generated report represents a fixed snapshot. Later changes to live Work Control data must not silently alter an already issued report.

## 4. Common Report Header

Every report contains:
- Lithosite Mine Services identity
- report title
- reporting period
- site/scope
- generated date/time
- prepared/generated by
- report ID
- data status / validation status

## 5. Daily Report

### Objective
Provide a concise operational record answering: **What happened today?**

### Required sections
1. Executive Summary
2. Work / Task Completed
3. Equipment Status
4. Work Front Status
5. HSE Events / Safety Notes
6. Maintenance / Downtime
7. Material Movement
8. Issues and Abnormalities
9. Site Map / Spatial Activities when available
10. KPI Summary
11. Outstanding / Carry-over Tasks
12. Supporting Evidence / References

### Daily KPI baseline
Where valid data exists:
- Planned / Scheduled Time
- Available Time
- Used Time
- PA
- UA
- EU
- Equipment population and exclusions
- Maintenance downtime

Invalid or incomplete KPI values must be shown as unavailable/validation required, not fabricated.

## 6. Weekly Report

### Objective
Provide management with performance and trend context answering: **How are we performing?**

### Required sections
1. Executive Summary
2. Planned vs Actual
3. Equipment Performance
4. Work Front Progress
5. HSE Summary
6. Maintenance and Downtime Analysis
7. Material Movement Summary
8. Issues and Recurring Issues
9. Outstanding Actions
10. KPI Trend
11. Key Highlights
12. Top Management Concerns
13. Recommended Actions

Weekly reports should emphasize aggregation, trends, comparison, and recurring conditions rather than repeating every daily transaction.

## 7. Monthly Report

### Objective
Provide management-level information answering: **What does management need to know or decide?**

### Required sections
1. Management Executive Summary
2. Monthly KPI
3. Target vs Actual
4. Equipment Performance
5. Work Front Progress
6. HSE Performance
7. Maintenance / Downtime
8. Material Movement
9. Major Issues / Events
10. Recurring Problems
11. Outstanding Actions
12. Trend vs Previous Month
13. Performance Highlights
14. Management Attention / Decision Required
15. Recommendations
16. Appendix / Evidence

The Monthly report must prioritize decisions, risks, trends, and exceptions over transaction-level detail.

## 8. Data Source Authority

Reports consume existing domain data and derived KPI results. They must not create a second operational truth.

Primary sources:
- Operations
- Equipment
- WorkFront
- Maintenance
- Issues
- Plans
- HSE
- Marker Location / spatial evidence
- Topography/map state where relevant
- KPI Foundation / finalized KPI snapshots

Raw domain records remain authoritative for their respective facts. Derived KPI values must retain their calculation policy and validation status.

## 9. KPI Lineage

KPI sections must preserve:
- baseline policy
- EU denominator policy
- effective-time rule
- calculation date/scope
- eligible population
- excluded population
- validation issues
- finalized snapshot/revision when applicable

A report must not silently recalculate a finalized KPI snapshot using a different policy.

## 10. Evidence and Traceability

Where a report statement depends on operational evidence, the report should be traceable to:
- source domain
- source record/reference
- reporting date/period
- evidence status

Spatial evidence may include marker IDs and map context. Detailed raw evidence belongs in the appendix or underlying system, not necessarily in the executive summary.

## 11. Status and Validation

Report generation states:
- DRAFT — report assembled but not issued
- READY — required data validated and report can be issued
- ISSUED — immutable report snapshot generated
- VALIDATION REQUIRED — one or more required inputs are incomplete or invalid

The system must never represent missing data as zero unless zero is an explicit source value.

## 12. PDF Output

PDF is the first formal delivery format.

Minimum PDF requirements:
- stable page layout
- report identity on every page
- page number
- generation timestamp
- clear period
- readable tables and KPI cards
- no clipped content
- no live UI dependencies
- consistent terminology between dashboard and report

Future output formats may include XLSX/CSV or other machine-readable exports, but they are outside this first contract.

## 13. Report Center

The future Report Center is the user-facing entry point.

Minimum controls:
- Daily / Weekly / Monthly
- reporting period
- site/scope
- Preview
- Generate PDF
- report status
- report history

Issued reports should have a report ID and remain distinguishable from live/current data.

## 14. Design Principle

The reporting hierarchy is intentionally:

**DAILY**
> What happened?

**WEEKLY**
> How are we performing?

**MONTHLY**
> What does management need to know or decide?

The report engine must preserve this distinction.
